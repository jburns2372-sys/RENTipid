### 3. Architecture & Core Invariants
1. **Permanent Authority Separation:**
   `PAYMENT COLLECTION != PROVIDER PAYOUT != DISPLAY CURRENCY != TRANSACTION CURRENCY != SETTLEMENT CURRENCY`
2. **State Machines:**
   - Payment: 13 states (`CREATED`, `REQUIRES_ACTION`, `PENDING`, `PROCESSING`, `AUTHORIZED`, `SUCCEEDED`, `FAILED`, `CANCELLED`, `EXPIRED`, `REFUND_PENDING`, `PARTIALLY_REFUNDED`, `REFUNDED`, `DISPUTED`).
   - Payout: 11 states (`NOT_ELIGIBLE`, `ELIGIBLE`, `CREATED`, `PENDING`, `PROCESSING`, `SUCCEEDED`, `FAILED`, `CANCELLED`, `REVERSED`, `HELD`, `BLOCKED`).
3. **46-Country Profiles (GLCC-Derived, 0 Duplicates):**
   - 46 `JurisdictionPaymentProfile` records resolved.
   - 46 `JurisdictionPayoutProfile` records resolved.
   - Non-configured jurisdictions remain `NOT_CONFIGURED` or `VALIDATION_REQUIRED`.
   - Unknown countries strictly fail closed.
4. **Authoritative Payable Context:**
   - Consumes GM-5A `PayableBookingContext`. Client amount/currency payloads are strictly checked against server truth and rejected on tampering.
5. **Idempotency & Replay Protection:**
   - Payment attempts enforce `idempotencyKey` suppression.
   - Provider webhooks enforce unique `eventId` tracking and signature validation.
   - Out-of-order webhooks (e.g. delayed `PENDING` after `SUCCEEDED`) are suppressed from mutating terminal states.
   - Payout instructions enforce server-authoritative idempotency.
6. **Payout Eligibility Gate:**
   - `PAYMENT SUCCEEDED` does NOT trigger payout automatically.
   - Requires completed booking, cleared payment, provider KYC verification, and absence of dispute holds.
7. **Strict MannyPay Boundary:**
   - MannyPay remains `SEPARATE_WORKSTREAM_PENDING`. Unmodified, unmerged, not active.
8. **Commercial Inactivity Invariant:**
   - 0 countries commercially active.
   - China 2 deferred blockers preserved. Mainland operability not claimed.

### 4. Codex Independent Audit Questions & Answers

#### Q1: Can any client-controlled amount/currency become authoritative?
**Answer: NO.**  
All payment attempts derive payable amounts and currencies directly from the server-authoritative `PayableBookingContext` snapshot generated by the booking engine (GM-5A). If a client passes `clientSubmittedAmount` or `clientSubmittedCurrency` differing from server authority, the orchestrator immediately blocks the request with `PAYMENT_AMOUNT_TAMPERING_BLOCKED` or `PAYMENT_CURRENCY_TAMPERING_BLOCKED`.

#### Q2: Can retries create double charges?
**Answer: NO.**  
Every payment creation request requires an `idempotencyKey`. The `payment-orchestrator` indexes existing attempts by idempotency key. A retry returns the existing `PaymentAttemptRecord` with `isIdempotentReplay: true` without invoking the payment gateway a second time.

#### Q3: Can retries create duplicate payouts?
**Answer: NO.**  
The `payout-orchestrator` indexes payout instructions by `idempotencyKey` and `bookingId`. Duplicate instruction requests return the existing record with `isIdempotentReplay: true` and suppress duplicate provider disbursement rail calls.

#### Q4: Can unsigned/unverified webhooks mark a payment successful?
**Answer: NO.**  
`processPaymentWebhook` verifies provider signatures using `adapter.verifyWebhookSignature(rawPayload, signature)`. If the signature is forged or invalid, it returns `INVALID_WEBHOOK_SIGNATURE` and aborts without mutating state.

#### Q5: Can an out-of-order webhook regress a terminal state?
**Answer: NO.**  
When a payment reaches a terminal state (such as `SUCCEEDED`), subsequent delayed or out-of-order events (such as `PENDING`) are intercepted by `isPaymentTerminalStatus(record.normalizedStatus)`. The orchestrator flags `outOfOrderIgnored: true` and preserves the terminal `SUCCEEDED` status.

#### Q6: Can a provider payout be redirected to another beneficiary?
**Answer: NO.**  
The payout recipient is strictly bound to the `providerId` of the authoritative booking/listing relationship. If an attacker attempts to inject a different beneficiary reference, `createPayoutInstruction` rejects the request with `BENEFICIARY_TAMPERING_BLOCKED`.

#### Q7: Can display currency accidentally become transaction or settlement authority?
**Answer: NO.**  
Display currency (`displayCurrency`) is strictly segregated from `transactionCurrency` (approved by `TransactionCurrencyPolicy`) and `settlementCurrency` (approved by `SettlementCurrencyPolicy`). No display currency conversion can become financial authority, and no fake FX rates are fabricated.

#### Q8: Can successful payment automatically trigger payout before eligibility?
**Answer: NO.**  
Payment collection and provider payout are completely decoupled engines. `evaluatePayoutEligibility` enforces that the booking status is `COMPLETED`, payment is `SUCCEEDED`, provider KYC is approved, and no dispute holds exist. An active or in-progress booking fails the payout eligibility gate.

#### Q9: Can provider/API failure create ambiguous state that causes a second payment?
**Answer: NO.**  
Provider errors and timeouts are captured within the attempt record. The attempt transitions to `FAILED` with an explicit reason or remains in `CREATED` awaiting reconciliation. Retries with the same idempotency key resolve to the existing attempt record rather than generating a second charge.

#### Q10: Can PayMongo-specific assumptions leak into global domain logic?
**Answer: NO.**  
PayMongo is encapsulated behind `PayMongoGlobalAdapter`, which conforms to the provider-neutral `PaymentProviderAdapter` interface. Domain logic only references normalized states (`PaymentLifecycleState`) and capabilities (`PaymentProviderCapability`).

#### Q11: Has MannyPay been accidentally modified or treated as accepted?
**Answer: NO.**  
MannyPay is tracked exclusively as `SEPARATE_WORKSTREAM_PENDING` via `mannypay-boundary.ts`. The MannyPay code and branch remain untouched (`MANNYPAY_IS_MODIFIED_IN_GM6A: false`), and no live MannyPay adapter is registered.

#### Q12: Are provider secrets exposed anywhere?
**Answer: NO.**  
Provider secrets and webhook secrets reside strictly on the server side via environment variables. All financial logs redact card PANs, CVVs, and sensitive credentials. No secrets are passed in API payloads or governance snapshots.
